# Audit and release readiness, 2026-11-14

A dated record of a whole-codebase pass before an APK release: the Rust core
and MLS crate, the Python engine and bridge, the Android app and its build,
and every dependency the APK ships. It describes the code at `rc.203`.

This is a developer's audit with AI assistance, like the ones before it. It is
not an independent audit, and nothing here replaces one.

## Result

| | |
|---|---|
| Vulnerabilities found in shipped code | none exploitable; 4 hardening fixes (H1-H4) |
| Functional defect found | 1 (F1: microphone during a call with the screen locked), fixed |
| Known-vulnerable dependencies shipped | none found (Rust, Python, i2pd, OpenSSL, libopus); AndroidX not checkable here (O3) |
| Blocks a production release | O1 (release signing key) and the device tests in O2 |

## Fixed

**F1. A call could lose the microphone when the screen locked.** Since
Android 11 an app in the background may use the microphone only from a
foreground service of type `microphone`; under any other type the capture
reads silence. The connection service was declared `dataSync` only (target
SDK 35). It now declares `dataSync|microphone` and claims the microphone type
for exactly the length of a call, 1:1 or group (`claimMicrophone`,
`connection/ServiceNotifications.kt`), returning to `dataSync` after. Android
allows the claim only while the app may start a microphone service (on
screen, as when Call or Answer is tapped); a refusal leaves the old behaviour,
is not retried during that call, and is traced as `microphone_not_claimed`.
Needs a device test (O2).

**H1. A corrupt MLS store aborted the app.** The release profile is
`panic = "abort"` with overflow checks, so any panic is the app dying.
`Rust/mls/src/storage.rs` unwrapped 38 decode/encode results and a queued
proposal looked up by its ref. All of those functions already return
`Result`; they now return `StorageError`. The store is only restored from an
AES-256-GCM sealed snapshot, so a tampered one was already refused; this
removes the abort for a damaged or inconsistent one.

**H2. `unwrap_key` trusted its caller for the length its slices assume**
(`Rust/src/at_rest.rs`). It checks length and magic itself now.

**H3. A registration reply carrying a DTD was parsed** (`android_bridge/
captcha.py`, bandit B314). XMPP forbids DTDs (RFC 6120 §11.1). Production
hands this function an element slixmpp has already parsed, so this was
reachable only by direct callers; a document with `<!DOCTYPE` or `<!ENTITY`
is now refused unread, with an entity-expansion test.

**H4. `Rust/mls/Cargo.lock` was never audited, and "locked, not built" was
asserted, not checked.** `cargo audit` there reported five advisories
(crypto-bigint 0.5.5 timing, two libcrux-kem panics, a libcrux-hmac-drbg
panic, SQLite). Each is the same triage as the core's lock: present only
through OpenMLS's optional providers. Re-verified with
`cargo tree -e all --features mls,android-opus --target all -i <crate>`: none
is in the shipped build (crypto-bigint 0.5.5 is compiled only by the MLS
crate's test-only `reference-interop` cross-check). CI now audits that lock
too and fails if any ignored crate appears in the shipped build, with ml-kem
as the positive control (`.github/workflows/rust-audit.yml`).

## Checked, nothing to fix

**Rust core and MLS crate.**
- `#![forbid(unsafe_code)]` in both. The only `unsafe` is the libopus FFI in
  `Rust/opus-codec` (14 blocks): packet length capped at the RFC 6716 maximum,
  output buffers sized to the capacity passed, each handle freed once.
- Every remaining `expect`/slice in production code was traced: each is
  either a fixed-length invariant (a 12-byte nonce, a 32-byte key, an HKDF
  length, a hex constant) or preceded by the length check it relies on
  (`group_voice::parse_header`, `import_sealed`, the container run reader,
  `AppLockRecord::parse`, `vault_open`).
- MAC, tag and confirmation comparisons go through constant-time equality;
  the one plain `==` on key bytes (`holds_mac_key`) is compiled only for tests.
- `cargo clippy --all-targets` (core with `mls`): no warnings; 13 targeted
  style allows, no blanket ones.
- Tests: core 227, MLS 77, all pass; every fuzz target compiles.

**Python engine and bridge** (`client/`, `android_bridge/`, `desktop_bridge/`).
- bandit: no high-severity finding; the one medium was H3. No `eval`, `exec`,
  `pickle`, `shell=True` or `os.system`; every `__import__` takes a constant.
- The subprocess calls are Termux and desktop helpers with argument lists; the
  one that carries text a peer influenced (a notification title) is cleaned
  and a leading `-` neutralised.
- No password, passphrase, key or seed reaches a log or print; the matches are
  event names ("stored", "session bound").
- Network input is bounded: OTR fragments (per fragment, per peer, in total),
  file offers, transfers (2 GiB), voice notes (16 MiB, 300 s).

**Android app and release build.**
- Backups off (`allowBackup="false"`, data-extraction rules), cleartext off,
  `FLAG_SECURE` on the one activity from creation.
- Exported: only `MainActivity`, for the launcher. The only action it reacts
  to from outside is `ACTION_OPEN_ARRIVAL`, which counts a tap that makes the
  app *ask* before showing anything.
- The service and the diagnostics FileProvider are not exported; the PDF
  renderer is an isolated process.
- The release variant is R8-minified, strips `android.util.Log`, and is not
  debuggable (CI reads it back from the built APK's manifest).

**Dependencies the APK ships.**
- Rust: `cargo audit --deny warnings` clean for the core's lock; the MLS lock
  clean under the H4 config.
- Python (hash-locked `android/app/python-lock.txt`): pip-audit, no known
  vulnerabilities. Desktop environment: none.
- Bundled i2pd 3.0.0.1 and OpenSSL 3.5.9, both pinned to a commit; libopus
  1.5.2. No 2026 advisory found for any of the three (the only i2pd CVE,
  CVE-2017-17066, is fixed since 2.17).

## Code structure (audit tidy 4)

The three largest Kotlin files were split. Kotlin has no partial classes, so
each part is either an interface the class implements by delegation or a set
of extension functions; no call site and no behaviour changed.

## Open: what still stands between this and a production release

**O1. The release APK is signed with CI's debug key.** No release key is
configured, so every published build says so, and an update may need an
uninstall. Only the owner can fix it: create a keystore once, keep it offline
and backed up (losing it means users cannot update), and add the four
repository secrets `.github/workflows/android.yml` reads
(`OTRV4PLUS_RELEASE_KEYSTORE_B64`, `_STORE_PASSWORD`, `_KEY_ALIAS`,
`_KEY_PASSWORD`). The steps are in [RELEASE_SIGNING.md](RELEASE_SIGNING.md).

**O2. Device tests.** Everything since rc.194 is tested by CI only. Before a
release: a call of a few minutes with the screen locked on the phone (F1),
the rc.202 delay fix (mouth-to-ear back near 0.6-0.7 s), and the rows the
release page lists as not yet verified (five-person group call, sign-up on a
just-started router, router log after a drop).

**O3. AndroidX libraries were not checked against an advisory database.**
OSV and GitHub's advisory API are unreachable from the audit environment.
Enabling Dependabot alerts on the repository covers this from then on.

**O4. Kotlin toolchain 2.0.21** (build-time only; CVE-2026-53914 was deferred
on 2026-11-11). Nothing from the toolchain ships in the APK; upgrading Kotlin,
the Compose plugin and AGP together is a change to make with CI, not before a
device test.

**O5. Not independently audited.** As the README and release page say.
